### [H-1] Private Swap Cashback Is Permanently Credited to the Vault Instead of the Trader

**Description**
There is an architectural flaw in the fee distribution logic between the zero-knowledge manager (`ZendexAmmManager`) and the swap router (`ZendexRouter`). 

In the Zendex architecture, real users execute private swaps using ZK proofs. The `AmmManager` coordinates this by releasing tokens from the `Vault`, calling the `Router` to swap them, and routing the outputs back to the `Vault`.

The specific root cause is found in `ZendexAmmManager.sol#_executeSwap`:

```solidity
$.router.swapTokensForExactTokens(
    IRouter.SwapTokensForExactTokensParams({
        amountOut: p.amountB,
        amountInMax: p.amountA,
        path: path,
        to: address($.vault), // <-- Tokens routed to Vault
        deadline: p.deadline
    })
);
```

Because the `AmmManager` must route the output tokens to the `ZendexVault` (to collateralize the user's newly generated encrypted commitment), it hardcodes the `to` parameter as `address($.vault)`. 

However, the `ZendexRouter` lacks a separate concept for the "economic beneficiary" of the trade. Inside `ZendexRouter.sol#_distributeFees`, the Router explicitly uses the `to` parameter (the output recipient) as the `trader` for reward accounting:

```solidity
uint256 amountToPair = _distributeFees(p.path[0], p.to, totalAmountIn);
// ...
IRewardsEngine($main.rewardsEngine).depositFees(token, trader, treasuryFee, cashbackFee, burnFee);
```

Consequently, the Router assumes the Vault is the trader, completely misattributing the cashback to the Vault contract.

**Impact**
Every affected private swap misattributes the entire cashback generated by the trade to the `ZendexVault` address instead of the swap's economic beneficiary.

As a result:
* The intended beneficiary receives **0 cashback** for the affected private swap.
* The full cashback amount is instead recorded in `RewardsEngine` under the `ZendexVault` address.
* The affected cashback is not recoverable by the user because `RewardsEngine.claim()` operates on `msg.sender`, while the Vault does not expose a mechanism to invoke `claim()` or otherwise transfer its `RewardsEngine` balance.

This does **not** result in loss of the user's principal swap funds. The impact is the permanent loss of the cashback/reward value associated with affected private swaps.

**Proof of Concept**
A complete executable Hardhat test script is provided alongside this report in `CashbackPoC.test.ts`. 

The execution simulates the vulnerable integration point between `ZendexAmmManager` and `ZendexRouter`:
1. A private swap is executed through `ZendexAmmManager`, which calls `swapTokensForExactTokens` with `to: address(vault)`.
2. The exact cashback fee configuration is extracted from the Router (`225` with a `1,000,000` denominator).
3. We record state deltas and calculate the exact expected cashback independently to avoid circular assumptions.
4. The test successfully asserts that:
   - `vaultCashback == expectedCashback` (The Vault incorrectly received the exact cashback fee).
   - `realUserCashback == 0` (The economic beneficiary received nothing).
   - The deployed `ZendexVault` contract lacks a `claim()` function or generic `execute()` fallback, mathematically freezing the funds in the `RewardsEngine`.

**Recommended Mitigation**
The core architectural issue is that the Router overloads the `to` parameter for two different purposes:
1. `to`: Where do the output tokens go?
2. `trader`: Who is the economic beneficiary of the rewards?

**1. Update `ZendexRouter.sol` to separate these concepts:**
Provide an explicit parameter for the reward beneficiary so the Router stops making assumptions based on token routing.

```solidity
function swapTokensForExactTokens(
    SwapTokensForExactTokensParams calldata p,
    address trader // <--- Explicit reward beneficiary
) external virtual ensure(p.deadline) returns (uint256[] memory amounts) {
    // ...
    uint256 amountToPair = _distributeFees(p.path[0], trader, totalAmountIn);
    // ...
    _swap(amounts, p.path, p.to); 
}
```

**2. Update the ZK Circuit and `ZendexAmmManager.sol`:**
The protocol must provide an authenticated mechanism for deriving or specifying the reward beneficiary independently from the swap output recipient. 

```solidity
$.router.swapTokensForExactTokens(
    IRouter.SwapTokensForExactTokensParams({
        // ...
        to: address($.vault), 
    }),
    p.cashbackRecipient // <--- Protocol passes the authenticated user address
);
```
